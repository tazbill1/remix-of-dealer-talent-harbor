## src/lib rules
- Quick feedback extends interview_scorecards with independent feedback fields; save_quick_interview_feedback is authenticated security-invoker, guards author/org/interview/store access and maintains one timeline event. UI saves are serialized; kit answers/submission stay untouched. Why: one interview/author row without stage changes, messaging or autosave races.
- Applicant notes use add_applicant_note (security invoker) to atomically append legacy notes and insert a note event with auth.uid(); the panel renders newest-first note events and updates its timeline cache immediately. Why: preserve existing notes, enforce existing RLS and avoid partial saves.
- Job manager assignment uses hiring_manager_user_id validated against org/store manager scopes; job_contact_options is authenticated and scoped. The old name is a derived compatibility cache for reports/messages. Escalation defaults use store HR/recruiter then group HR/admin; explicit overrides stay unchanged. TeamInvites keeps its existing admin-only permission. Why: stable account assignments without unrelated feature or access changes.
- Staff bonus display uses referral-bonus-display.ts: pre-hire reads job tier/org days; post-hire reads saved bonus amount/due date. TierSettings/ProgramRules are only in HR Settings > Employee referral bonus. Why: one setup path, no award recalculation.
- Referral enrollment uses token-derived public signup with service-only duplicate-safe SQL, durable per-store/IP limits, and HR-authorized chunked CSV import; directory RPC is RLS security-invoker and pages 50 rows. Why: preserve codes/bonuses and store isolation at employee scale.
- Event coverage uses database scope helpers and RLS-authorized options; legacy preserves old scans, new scans derive covered stores server-side, and event analytics group by each applicant's store. Why: multi-store events cannot leak access or lose attribution.
- Applicant lists reuse Ask's provider/model/options via an authenticated filter-only function; AI sees RLS-scoped catalogs, never applicant rows, and validated output only sets URL filters. Contact/week math is pure and tested. Why: no selection, messaging, data or access changes.
- Bulk confirmation uses fresh eligibility/channel/store counts and bulkConfirmationAllowed for typed counts at 25+ actual recipients. Why: skips and dual-channel deliveries must not confuse recipient confirmation.
- Applicant select-all uses selectAllShown over the filtered/tab-visible IDs only. Why: hidden applicants must not enter a newly built message list.
- Apply forms use tested applicationScan in scan.ts to prefer current QR codes and omit remembered scans when the URL has an explicit source; referral capture remains separate. Why: browser history cannot override a new source-tagged link.
- Texting workflows (welcome, manager summary/nudge/escalation, reminders, check-ins) live in src/lib/workflows: rules in rules.ts (pure, tested), the scheduled runner in run.server.ts, fixed-meaning manager replies in replies.server.ts.
- Weekly summaries use tested weekly-summary.ts and weekly-summary.server.ts via workflows cron, unique weekly_summaries member/week; automations.weeklySummary settings. Why: staff emails follow practice/opt-out/footer rules without applicant queues.
- Status rules use tested status-rules.ts and status-rules.server.ts via workflows cron; settings are automations.statusRules, edited only through saveStatusRules/can_post_jobs. Clocks start on activation unless include-waiting is checked; applicant email is opt-in. Why: no surprise backlog moves or messages.
- Display wording helpers live in src/lib/display.ts (plural, sourceLabel, isTestName; pure, tested). Why: counts, source names and test-applicant hiding must read the same on every page without changing stored values.
- LinkedIn profile links normalize through src/lib/linkedin.ts (pure, tested); the apply form and staff panel share it. Why: one validation rule and one canonical stored form.
- Store setup rules (required fields, US phone, defaults, Missing info) live in src/lib/store-validation.ts (pure, tested) and the shared StoreFormFields; app-side only. Why: create and edit forms enforce the same rules while incomplete existing stores keep working.
- "Still reviewing" check-ins (automation `waiting`, defaultOff) use tested dueWaitingCheckin in workflows/rules.ts and waitingCheckinPlan in run.server.ts; history is the messages table (purpose waiting_checkin_N), no extra table. Only New/Screening, never the first text, stops on blocked/4 sent/45 days. Why: no surprise texts and no schema change.

- Employee referrals: can_manage_referrals RLS (store staff/regional leaders read assigned stores); public ?ref= via referrer_by_code; one bonus per hire from the create_referral_bonuses trigger (tier locked from jobs.referral_tier_id or suggest_referral_tier, eligibility from referral_settings, ineligible = status not_eligible); due alerts and quarterly drawing entries by referrals.server.ts in workflows cron; winners only via pick_referral_drawing_winner; rules mirrored in src/lib/referrals.ts. Why: every hire path is judged once in the database; no texts or emails.
- AI-use disclosure wording, the first-message line and HUMAN detection live in src/lib/ai-notice.ts (pure, tested); apply saves an ai_notice consent row, and HUMAN pauses the assistant and sets needs_attention "Wants a person", which stops automated candidate texts/emails. Why: one source for disclosure wording and opt-to-human handling.
- In-app alerts live in the notifications table (recipient-only reads/mark-read, platform admins read all, service-role inserts); recipient choice and wording are in src/lib/notifications.ts (pure, tested), created by notifications.server.ts; the optional manager email is automations.humanAlert.email (off by default). Why: alerts reach only the right store staff without new messaging paths.
- Manager "Your to-do" on the dashboard uses tested managerTodo in src/lib/manager-todo.ts over authenticated RLS reads (no new table); "Decide" is Screening, the same group the summary/nudge texts cover. Why: app and texts agree, and store access rules scope the list.
